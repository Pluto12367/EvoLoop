# EvoLoop 第二阶段：有界策略自改进

## 目标与范围

用户选择了“提示词与解题策略自改进”路线。Agent 根据开发题集上的执行结果提出通用解题策略，再对新策略进行评测；只有通过晋升规则的策略才成为同一状态目录中后续改进实验的起点。形成 evaluate → propose → evaluate → select 的可审计闭环。

这是提示词层面的实验性改进，不是训练模型权重。继续使用 Python 3.12+、dotenv、pytest、现有模型与 Docker 执行器接口；不引入前端、数据库、复杂 Agent 框架或自动源码修改。

## 方案选择

- 提示词与解题策略：用户已选。变化范围小、策略可版本化，能够直接比较同一评测集上的表现。
- 经验记忆与检索：后续候选，会引入记忆质量、检索与数据污染问题，本阶段不实现。
- 自动修改源码：后续候选，需要额外的变更验证、权限和回滚机制，本阶段不实现。

用户于 2026-10-29 确认先用模拟模型验证该自改进流程；以下细节作为第二阶段实现约定。

## 一个实验的流程

1. 读取一个固定 benchmark，开发集与保留集非空，题目 ID 唯一且不重叠。第一版随项目提供小型 Python 编程 benchmark；旧的两道示例题继续保留。
2. 加载当前 active strategy；若没有，使用版本化的 baseline strategy。记录 benchmark 内容哈希、模型名称、策略文本、执行参数和预算。
3. 在开发集评测 baseline，最多按现有规则每题尝试三次。
4. 策略提议器只读取当前策略与开发集反馈，生成通用解题指导。反馈只含题目公共描述、通过/失败/超时等类别、白名单错误摘要和汇总指标，不包含测试输入、预期答案、原始异常输出、密钥或保留集数据。
5. 在相同开发集评测候选策略。通过率严格提高才成为下一轮 incumbent；相同通过率不晋升。每轮继续使用当前最优策略，拒绝的候选保留在日志里。
6. 改进轮数耗尽、连续两轮无提升或预算耗尽时，停止提出候选。若预算不足以完成后续比较，则将实验标为 incomplete，不晋升任何持久策略。
7. 冻结开发集选出的最终候选。只在实验末尾分别评测 baseline 和最终候选的保留集表现；保留集结果不进入策略提议器，不触发继续调参。
8. 最终候选的开发集通过率严格提高，且保留集通过率不低于 baseline，才晋升 active strategy。否则保持原策略。没有更优开发候选则跳过保留集评测，记录 no_improvement。

保留集采用固定、可重复的检查规则；小型题集的单次分数只证明本次实验表现，不能证明真实模型的统计显著提升。重复运行同一保留集可能造成间接过拟合，报告需注明 benchmark ID/哈希以便用户识别复用。

## 输入与组件

- `TaskSpec`：只含公共题目 ID、描述、函数名，模型客户端只能接收此视图。完整 `Problem.tests` 只提供给执行器。
- `Strategy`：版本 ID、父版本、策略文本。策略是有长度限制的普通文本，不执行其内容、不解析为配置，不允许修改执行器、测试或评分函数。
- `StrategyProposer`：可替换接口；输入策略和开发反馈，输出候选策略文本。真实客户端使用模型调用，离线模拟提议器提供可预测行为。
- `Benchmark`：开发题集与保留题集，具有唯一版本标识与内容哈希。
- `Evaluator`：复用 Agent/DockerExecutor，计算最终通过题数、总题数、通过率、首次尝试通过率、总尝试数和耗时，并保留每道题的每次尝试。
- `ImprovementLoop`：管理轮数、调用预算、开发集选择、最终保留集门槛、停止原因与策略晋升。
- `StrategyStore`：以 JSON 保存 active strategy 和实验记录；同一目录内通过临时文件与原子替换写入。失败实验不覆盖 active strategy。第一版单进程运行，不支持并发写同一状态目录。

现有 `python -m evoloop` 行为保留。所有可替换组件的类型协议清晰，不把核心编排绑定在单一提供商上。

基准题集在一次实验开始时复制为独立快照并计算内容哈希；模型输入使用独立 `TaskSpec`，不含对可变测试列表的引用。每次判题得到自己的输入副本，避免解答函数修改列表参数而改变后续评测。验证开发集与保留集所有题目都至少包含一个测试，拒绝空集、重复 ID 和测试无法序列化的题集。每次评测采用相同题目顺序、每题尝试上限和模型设置，报告记录完整基准哈希及分集哈希。

## 预算与故障

- 默认最多改进 2 轮，允许配置 1–5 轮；每道题仍最多 3 次尝试。
- 默认最多 100 次模型调用，生成答案和提出策略都计入；先扣预算再发起调用，失败调用同样计入，绝不超额。
- Docker 不可用、评测基础设施异常或模型通信异常属于实验故障，不将它们计为策略能力下降；记录错误并终止实验，不晋升。
- 一般代码运行异常/超时按现有判题规则计分，但不会把原始输出反馈给模型。
- 候选文本为空、超长或格式无效时拒绝并记录，消耗一次提议调用，不执行或保存为 active strategy。
- 输出完整 JSON 记录，含完成/未完成状态、停止原因、每轮候选和父策略、评测指标、预算使用、晋升决定以及全部题目尝试。

故障来源使用明确的结构化类别区分模型错误、执行基础设施错误与生成代码错误，不能依赖匹配错误文本作区分。故障报告保留已完成的题目和失败前的尝试信息，但只输出固定的错误类别和白名单摘要。实际执行时间、模型调用数量作为成本指标，不用于候选晋升，避免把网络抖动误判为策略提升。

策略文本长度上限为 4000 字符，去除首尾空白后必须非空；候选内容与当前策略相同时记录重复候选，不重新评测，计入无提升轮数。版本 ID 由策略文本哈希确定，父版本单独记录。不向提议器提供原始代码、测试序号、完整执行报告或保留集元数据；只构造公共题目视图、汇总指标及不含测试序号的固定错误类别。

状态保存顺序：先写入完整实验报告与候选策略档案，成功后最后原子替换 active strategy。中途文件写入失败不得修改原 active strategy；若实验终止或写入失败，CLI 返回非零且说明未晋升。原子替换保证单文件完整性，不声称多个文件间有数据库事务或断电恢复能力。

## 命令行与文件布局

拟新增：

```text
evoloop/
  strategy.py       # 策略和提议器协议/实现
  benchmark.py      # 固定 benchmark 与校验
  evaluation.py     # 指标、模型调用预算与批量评测
  improvement.py    # 有界自改进编排
  storage.py        # JSON 原子保存
tests/
  test_strategy.py
  test_benchmark.py
  test_evaluation.py
  test_improvement.py
  test_storage.py
```

拟提供入口：

```powershell
python -m evoloop --improve --model mock --rounds 2 --state-dir runs/demo
python -m evoloop --improve --model openai-compatible --rounds 2 --state-dir runs/real
```

标准输出为完整 JSON 报告；状态目录保存单独实验报告和 active strategy。运行产物加入 Git 忽略。原来的普通解题入口可读取显式指定的策略，不自动改变旧示例流程。

## 离线模拟的含义

使用固定、明确标注的模拟策略客户端演示 baseline 失败、候选修复、晋升或回退。生成代码仍由真实 Docker 执行器判题；单元测试可注入确定性的执行器替身。模拟策略对预设策略文本作确定性响应，只验证流程正确，不作为模型学习或真实能力提升的证据。

## 验收

1. 不配置 API 密钥，能用模拟模型和 Docker 完成 baseline → 候选 → 比较 → 晋升的整个实验，生成持久 JSON 报告。
2. 能拒绝开发集无提升的候选；保留集退步时保持原策略；模型/执行器不可用或预算不足时不晋升。
3. 预算和轮数均不超限，每道题仍最多三次尝试。
4. 模型不接收测试用例，策略提议器从不接收保留集；测试对这些边界作明确断言。
5. 策略可以从状态目录加载，晋升过程保留父版本和旧版本；失败写入不破坏原 active 文件。
6. 保留现有功能；运行全套 pytest，并单独报告真实 Docker 集成验证是否执行。

## 已知限制

继续沿用现有 Docker 判题器，它适用于受控实验，尚未实现抗评测篡改的强隔离。提议器和解题器都无权改变判题器、测试、阈值或预算；这不消除生成代码干扰容器内评测的现有限制。强沙箱与更大、独立的统计评测作为后续工作。
